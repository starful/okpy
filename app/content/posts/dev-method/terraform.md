# プラットフォームエンジニアリングチームの立ち上げ方:Terraformモジュール標準化からセルフサービス化まで

![cover](https://storage.googleapis.com/ok-project-assets/okpy/20261123193943.jpg)


## はじめに

クラウドインフラの複雑化とともに、各開発チームが個別にTerraformコードを書き、個別にAWSやGCPのリソースを管理する体制は、組織が大きくなるにつれて限界を迎えます。同じようなVPC構成、同じようなECSサービス定義、同じようなIAMポリシーが、リポジトリごとに微妙に異なる形で量産され、セキュリティレビューやコスト管理の負荷が雪だるま式に増えていく——これは多くの組織が通る道です。

プラットフォームエンジニアリングは、この問題に対する一つの解答です。インフラやCI/CDの共通部分を「プラットフォーム」として切り出し、専門チームがそれを整備・運用することで、アプリケーション開発者は本来の価値創出に集中できるようにする、という考え方です。本稿では、Terraformモジュールの標準化を起点に、どのようにセルフサービス化されたプラットフォームへ発展させていくか、立ち上げの実務的な進め方を解説します。

## 概念:プラットフォームエンジニアリングとは何か

プラットフォームエンジニアリングは、「内部開発者プラットフォーム(Internal Developer Platform, IDP)」を構築・運用する専門領域です。SREがシステムの信頼性に責任を持つのに対し、プラットフォームエンジニアリングはシステムを扱う「開発者の生産性」に責任を持つ、という違いがあります。

重要なのは、プラットフォームエンジニアリングは単なる「共通ライブラリ作り」ではないという点です。目的はあくまで、開発チームがインフラの詳細を意識せずに、安全でベストプラクティスに沿った環境を自分たちのペースで手に入れられるようにすることにあります。この「自分たちのペースで」という部分が、セルフサービス化の核心です。

典型的な成熟度の進み方は次のようになります。

1. **個別対応フェーズ**: 各チームが自前でTerraformを書き、インフラチームがレビューやサポートを個別に行う
2. **標準化フェーズ**: よく使う構成をモジュール化し、共通の書き方・レビュー基準を整備する
3. **セルフサービス化フェーズ**: 開発者がインフラチームを介さずに、承認済みのモジュールを使って自分でリソースを申請・作成できるようにする
4. **プラットフォーム化フェーズ**: ポータルやCLIツールを通じて、インフラ以外の要素(オブザーバビリティ、シークレット管理、権限設定など)も含めて一括提供する

いきなり4に飛ぼうとして失敗する組織は非常に多いです。段階を飛ばさず、まず2の標準化を確実に終えることが成功の鍵になります。

## 現場での進め方

### ステップ1: 現状の棚卸しから始める

最初にやるべきは、既存のTerraformコードを横断的に見渡し、「どのリソースパターンが繰り返し使われているか」を洗い出すことです。VPC、EKS/ECSクラスタ、RDSインスタンス、S3バケット、IAMロールなど、ほぼ全チームが似たような構成を持っていることが多いはずです。

このとき、コードの重複を数えるだけでなく、「過去半年のインシデントやレビュー指摘のうち、どれだけがインフラ設定ミスに起因しているか」も合わせて調べておくと、後でステークホルダーに説明するときの説得材料になります。

### ステップ2: 小さく始めてモジュールを標準化する

最もリスクが低く効果が見えやすいリソースから着手します。多くの場合、それは「S3バケット」や「IAMロール」のような、仕様がシンプルでセキュリティ要件が明確なものです。いきなりネットワーク全体やKubernetesクラスタのモジュール化に挑むと、要件のすり合わせに時間がかかりすぎて最初の成功体験を得る前に失速しがちです。

モジュール化の際は、次の3つを必ずセットで設計します。

- **入力変数のインターフェース**: 利用者が意識すべきパラメータを最小限に絞る(例: `environment`, `team`, `size` 程度)
- **デフォルトのガードレール**: 暗号化、タグ付け、パブリックアクセス禁止などをデフォルトで強制し、オプトアウトを難しくする
- **バージョニングとドキュメント**: Gitタグでモジュールをバージョン管理し、変更履歴とサンプルコードを必ず併記する

### ステップ3: 利用チームを巻き込んで反復する

モジュールは一度作って終わりではありません。最初の1〜2チームに使ってもらい、フィードバックを得て改善するサイクルを数回回すことが重要です。この段階でプラットフォームチームと利用チームの間に信頼関係を作れるかどうかが、後のセルフサービス化の受け入れられやすさを左右します。

社内でモジュールの存在と使い方が伝わらなければ意味がないので、社内Wikiやリポジトリの README に加えて、定例の技術共有会で実演することも効果的です。

### ステップ4: セルフサービス化の仕組みを整える

標準モジュールが複数チームで安定して使われるようになったら、次は「インフラチームを介さずにリソースを作れる」仕組みを整えます。具体的には次のような構成が一般的です。

- Terraformモジュールを呼び出すリポジトリ(あるいはプルリクエスト)を、各チームが自分で作成できるテンプレート化
- CIパイプラインでの自動検証(`terraform plan` の自動実行、ポリシーチェック、コスト試算)
- 一定の基準を満たしたプルリクエストは人によるレビューなしで自動承認・適用する「ガードレール付き自動化」
- Backstageのような内部ポータルを使った、カタログ形式でのセルフサービス申請

ここで注意したいのは、「セルフサービス=レビューを一切しない」ではないということです。ガードレールの設計によって安全性を担保した上で、日常的な承認作業をなくしていく、という考え方が正しいアプローチです。

### ステップ5: プラットフォームチームの体制を作る

実務が進むにつれて、プラットフォームチームの役割も明確にしていく必要があります。多くの組織では以下のような職能を置きます。

- モジュール設計・保守を担当するプラットフォームエンジニア
- セルフサービス基盤(ポータル、CI/CD)を構築するツール担当
- モジュールのセキュリティ基準を定めるセキュリティ連携担当
- 利用チームからの要望を取りまとめるプロダクトオーナー的役割

小規模な組織であれば、これらを兼務する2〜3名のチームから始めて問題ありません。重要なのは「プラットフォームは社内向けのプロダクトである」という意識を持ち、利用チームを顧客として扱うことです。

## メリットと注意点

### メリット

- **開発チームのリードタイム短縮**: インフラ申請の待ち時間がなくなり、新規サービスの立ち上げが速くなる
- **セキュリティ・コンプライアンスの一貫性**: ガードレールがデフォルトで適用されるため、設定ミスによる事故が減る
- **インフラチームの負荷軽減**: 個別の質問対応やレビューが減り、プラットフォーム自体の改善に時間を割けるようになる
- **コストの可視化と最適化**: 標準化されたタグ付けやサイズ指定により、コスト分析がしやすくなる

### 注意点

- **過剰な抽象化のリスク**: モジュールを汎用化しすぎると、逆に使いにくく複雑になる。「8割のユースケースをカバーする」程度を目安にし、残り2割は個別対応を許容する柔軟性を残す
- **ガバナンスの形骸化**: セルフサービス化を急ぐあまり、レビューをなくしただけでガードレールの設計が不十分だと、事故の温床になる
- **チーム間の温度差**: 標準化を「押し付け」と感じる既存チームも出てくる。強制ではなく、移行のメリットを示しながら段階的に移行してもらう姶勢が重要
- **継続的なメンテナンスコスト**: モジュールはクラウドプロバイダのアップデートに合わせて継続的に更新が必要であり、「作って終わり」にはならない

## 小さな実践例

ここでは、S3バケットの標準モジュールを例に、簡単なTerraformコードのイメージを示します。実際の値やポリシーは組織のセキュリティ要件に合わせて調整してください。

```hcl
module "app_bucket" {
  source  = "git::https://example.com/platform/terraform-modules.git//s3-bucket?ref=v1.2.0"

  team        = "payments"
  environment = "production"
  purpose     = "invoice-archive"

  # デフォルトで暗号化・パブリックアクセス禁止・ライフサイクル設定が適用される
}
```

利用チームが指定するのは「どのチームが」「どの環境で」「何のために」使うかだけで、暗号化方式やアクセス制御、バージョニングの有無といった詳細はモジュール側のデフォルトに委ねます。これにより、利用者はセキュリティの専門知識がなくても安全な設定を手に入れられ、プラットフォームチームは基準を一箇所で管理できます。

さらにセルフサービス化を進める場合、このモジュール呼び出しをテンプレートリポジトリとして用意し、`cookiecutter` やカスタムCLIで必要な値を入力するだけで雛形のプルリクエストが自動生成される、という形にすると、開発者の体験がさらに向上します。

## FAQ

**Q1. プラットフォームエンジニアリングチームは何人くらいから始めるべきですか?**

決まった人数の目安はありませんが、専任で2〜3名確保できると現実的に回り始めます。兼務体制で始める場合は、まず「最も使用頻度の高いリソース1〜2種類のモジュール化」のように対象を絞り込み、小さな成功を積み重ねてから体制を拡大するのがおすすめです。

**Q2. 既存のTerraformコードが多すぎて、全部をモジュール化するのは現実的ではありません。どう優先順位をつければよいですか?**

「利用頻度が高い」「過去にインシデントやレビュー指摘が多かった」「セキュリティ要件が明確で仕様がブレにくい」という3つの軸で評価し、スコアの高いものから着手するのが実務的です。全リソースをモジュール化する必要はなく、効果の大きいところから着手し、残りは個別対応のまま運用し続けても問題ありません。

**Q3. セルフサービス化すると、インフラチームによるレビューがなくなって品質が落ちませんか?**

レビューを「なくす」のではなく、「事前のガードレール設計に移す」と捉えるのが正確です。自動化されたポリシーチェックやコスト試算、モジュール自体に組み込まれたベストプラクティスによって、人によるレビューが担っていた役割の多くを代替できます。ただし、新しいリソースタイプの追加や既存モジュールの大きな変更については、引き続き人によるレビューを残すなど、リスクに応じた使い分けが現実的です。

## まとめ

プラットフォームエンジニアリングチームの立ち上げは、一足飛びにセルフサービス化を目指すのではなく、現状の棚卸し、小さなモジュール標準化、利用チームとの反復、そして段階的な自動化という順序を踏むことが成功の近道です。プラットフォームを「社内向けのプロダクト」として捉え、利用チームの体験を継続的に改善していく姿勢が、長期的に組織全体の開発速度と安全性を両立させる基盤になります。
