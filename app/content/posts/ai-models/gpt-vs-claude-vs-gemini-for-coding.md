# GPT-4.1 vs Claude Sonnet 4 vs Gemini 2.5 Pro：コーディング用途の徹底比較（2026年8月）

![cover](https://storage.googleapis.com/ok-project-assets/okpy/20260814080312.jpg)

> **検証の前提**：想定は **2026年8月**。Cursor / Copilot / Claude Code などの **ツール比較ではなく**、背後で呼ぶ **モデル** の比較です。モデルIDと料金は変わるため、表には検証日を残してください。

クラウド記事の「EKS vs GKE vs AKS」と同じく、三強を同じ軸で並べます。

- **OpenAI GPT-4.1**
- **Anthropic Claude Sonnet 4**
- **Google Gemini 2.5 Pro**

対象タスクは次の三つに限定します。

1. **リファクタ**（可読性・構造化、挙動維持）  
2. **テスト生成**（境界値・回帰の種）  
3. **レビューコメント**（リスク指摘、質問の質）

---

## 各モデルの概要（コーディング視点）

### GPT-4.1

広く使われているため、チーム内の「当たり前の第一候補」になりやすい。パッチ提案の形式を揃えやすく、レビュー文化との相性が良い現場が多いです。大規模リポジトリではコンテキスト設計（どのファイルを渡すか）が勝敗を分けます。

### Claude Sonnet 4

長い差分や複数ファイルを読ませるレビュー・リファクタで評価されやすい印象。説明文が丁寧で、レビューコメントの「なぜ危険か」が伝わりやすい反面、提案が冗長になることもあります。

### Gemini 2.5 Pro

長いコンテキストや、コード＋設計ドキュメントを同時に渡す用途で候補になりやすい。Google系CIや社内ドキュメント基盤と組み合わせる組織では運用メリットが出ます。出力の安定性はリポジトリ特性で差が出るため実測必須です。

## ユースケース別ガイド

### リファクタ

- **小さな関数抽出・命名**：三モデルとも実用。差は説明の長さ。  
- **モジュール境界の見直し**：差分が大きいほど Claude / Gemini の長文耐性が効く。  
- **必須**：テストまたは手動シナリオを先に固定し、「挙動維持」をプロンプトに明記。

### テスト生成

- 生成物は **草案**。カバレッジ数字より、境界値の列挙品質を見る。  
- フレークしやすいE2Eより、まず単体・契約テストから。

### コードレビュー

良いレビューは「正解の指摘」より **検証可能な質問** です。

| 良い指摘の例 | 避ける例 |
|---|---|
| 「この null は API 契約上あり得る？テストは？」 | 「もっと綺麗に書いて」 |
| 「N+1 の可能性。ログで確認を」 | 「性能が心配」（根拠なし） |

## 料金・運用

1. **PRごとに上位モデル**は高くつきやすい → 変更行数やリスクラベルで振り分け  
2. **秘密情報**：リポジトリ丸ごと送信ポリシーを先に決める  
3. **再現性**：temperature 低め、モデルID固定、プロンプト版管理  
4. **人間が最終承認**：マージ権限はモデルに渡さない

| 振り分け例 | モデル帯 |
|---|---|
| typo・小修正 | 小型（別稿の mini/Haiku/Flash） |
| 通常PR | 本稿の三強のいずれか |
| 認証・課金・データ削除 | 上位＋人間レビュー必須 |

## 選び方

1. 社内の代表PRを3本固定（リファクタ／テスト／レビュー）  
2. 三モデルに同じコンテキストで投げ、採点表を埋める  
3. 「指摘の再現性」「パッチの適用しやすさ」「無駄な冗長さ」を見る  
4. 第1候補とフォールバックをREADMEに書く  

> ミーティング一文：「IDEを増やす前に、GPT / Claude / Gemini を同じPR3本で採点して第1候補を決めましょう。」

## FAQ

**Q1. コーディング特化モデルだけ使えばよい？**  
A. 名称より実測です。特化を名乗っても、自社言語・設計流儀では差が出ます。

**Q2. エージェントに任せる方がよくない？**  
A. エージェントはオーケストレーション。品質の下限はモデルとコンテキスト設計で決まります。先にモデルを測る方が失敗が少ないです。

**Q3. 出力をそのままマージしてよい？**  
A. いいえ。テストと差分レビューが前提です。モデルは高速な草案生成器です。
